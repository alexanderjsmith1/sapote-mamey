### Workbook re-ingest and validator scope

The monolith's §-1.7 describes intended keyed, nondestructive merges and field-level logs. Its §-1.17 describes a different implemented path: current `update_master_workbook` removes prior rows for the incoming strain on an explicit canonical-sheet allowlist and appends new deterministic rows. A hand-entered value on a removed row is not carried forward automatically. Additional sheets are preserved by default, but preservation of a sheet does not preserve deleted row values. The “safe re-run” claim means replacement avoids duplicate allowlisted strain rows; it does not guarantee preservation of annotations, the prior independent cohort roster or all scientific judgments. The append-history exceptions include `A3_Run_Manifest`, `H1_Handoff_Log` and `H2_Gap_Queue`, rather than one universal merge-log sheet. These logs are not a field-by-field old/new value audit.

`python -m mamey.workbook_schema_check <master.xlsx>` checks the coded canonical master schema, required sheet/header presence and selected consistency rules. It does not validate the separate per-strain workbook. Its current input is one workbook; it has no before/after source pair or independent expected cohort roster, and does not implement the monolith's claimed duplicate-key reconciliation, deletion detection, interpretive-field prohibition or provenance conflict adjudication. Auto mode uses the fast path at 26 strain rows or more; it skips the A2/B1 orphan scan. `--full` selects the deeper available checks; `--v12` additionally enables the non-frozen D5/Activity_Ref rules. Read the JSON `validation_path`, errors and warnings; neither flag expands this into a complete scientific or provenance audit. The writer's `H1_Handoff_Log.validation_result = PASS` is a fixed producer value, not evidence that this standalone validator was invoked.

The direct writer atomically saves the supplied output path; it does not make an immutable history archive or serialize the entire read/modify/write transaction. The CLI `--master` path adds an advisory shared-master lock and publishes a complete file, while writing a date/strain-named Master_After file and package copy. Repeated same-day names can target the same output path; the monolith's “immutable snapshot” promise should not be inferred from that filename. Before an explicitly authorized re-ingest, retain an independently named, hashed before state outside the mutable target; after it, validate the resulting canonical master and compare the independent expected roster and operator annotations against the before state. Record the actual producer, paths, hashes and validation output. Preservation and reconciliation of annotations remain owner decisions; this entry grants no permission to overwrite user evidence or run a workflow.


### Output packages and conservation checks

The encyclopedia's §II.7 is an archival output map. Use actual manifest paths and producer receipts rather than assuming that the chapter's unprefixed illustrative filenames identify every present output.

The chapter's “nothing ... silently lost” conservation guarantee is broader than the owners implement. The standalone `mamey.boundary_audit` compares record/verdict aliases and selected rule/tier invariants and returns nonzero for reported problems. During `_write_package`, the CLI calls that audit as instrumentation: it writes `<strain>_boundary_audit.json` and warns on findings; exceptions are caught and warned. This call does not itself hard-stop package writing. Do not infer a successful boundary audit from package creation or MAMEY_COMPLETE. Inspect the actual receipt and errors, and record a separate audit-review hold if it is missing, skipped or failed; keep the producer package status distinct.

`tools/evidence_conservation_audit.py` is a separate two-JSON audit covering five selected diagnostic categories. It explicitly leaves cluster-comparison details, pfam2go and genefunctions outside coverage. Its package operand is a JSON **file**, not a package directory; record the exact raw/package JSON paths and hashes because audit output depends on which JSON was supplied. The current checks use an opaque serialized token blob: TIGRFAM checks aggregate token occurrence counts, substrate/product/RiPP checks bounded token presence, and active-site checking detects category text. These checks cannot prove each diagnostic value survived at its original strain / full node-or-contig / region / BGC alias. They also do not prove production, activity or physical linkage. Package validator statuses describe the selected extraction/integrity/judgment checks actually run. Gold completeness can be JUDGMENT_PENDING while overall status is MAMEY_COMPLETE. Neither this label, a zero CLI exit, file presence nor checksums establishes every source-evidence category's conservation or scientific correctness. Distinguish package checks, standalone boundary audit, selected source-token conservation and identity-bound source comparison in the handoff evidence. ### Interruption, continuation and observed completion

The monolith's project-state/checkpoint and Batch Controller recipes describe intended session bookkeeping. They do not establish that the current CLI automatically writes this project-state schema or restarts an interrupted extraction from a checkpoint CSV. Current `python mamey_run.py resume <package_dir>` prints a package/judgment briefing (optionally JSON); it reads manifest, triage and judgment-register data to suggest analysis work. It neither executes extraction nor consumes the monolith's completed/deferred strain lists. “Continue” in historical prose is not permission to start deferred jobs or rerun inputs. Select the next bounded task from actual saved evidence and current human authorization.

A resume brief is not a completion verifier. Missing/unreadable triage or register data can reduce to empty inputs; the current renderer can then say “All BGCs complete” at 0/0. Its `strict_runnable` flag checks narrative path existence, not content or the compiler's complete acceptance contract. Neither a directory, report filename, output ZIP nor that briefing proves native terminal execution. Rebind package/strain identity, input hash, exact bundle build, actual terminal status, validation receipt, applicable checksums and independent expected scope before reusing outputs. Keep unknown/missing/unreadable evidence explicitly unresolved instead of interpreting an empty denominator as success.

Current package status vocabulary is `MAMEY_COMPLETE`, `RECOVERY_VALIDATED`, `RECOVERY_NEEDED`, `PARTIAL_FAILED`; `terminal_status`, validator status, issue count and judgment progress are separate fields. RECOVERY_VALIDATED means validated recovery rather than uninterrupted execution; RECOVERY_NEEDED requires review/recovery; PARTIAL_FAILED must not be merged as complete. These differ from the monolith's four checkpoint labels. The package-status inference helper defaults to MAMEY_COMPLETE when there is no validator status or recovery marker, and gives an explicit valid manifest package_status priority over markers. Such inferred or previously declared labels alone do not prove the current run finished; preserve their provenance and compare the current terminal/validation evidence rather than promoting one stale field.

The runner appends phase receipts on a best-effort basis; START without a paired observed END/ERROR is incomplete evidence, and a phase END is local to that phase. Receipt writes can fail and warn, so no receipt is not proof that a phase never ran. Monotonic timing pairs are meaningful within the producing process, not as an absolute clock across restarts. On supported POSIX systems the run directory uses an advisory lock; the lock filename's existence does not establish a live owner. The lock helper has unsupported-platform/I/O fallbacks, so do not promise universal exclusion. Inspect process/producer state before another write, preserve the interrupted evidence, and retain one independently named candidate when a rerun is authorized. An input/code/schema change or a successful newer manifest is a reason to assess reuse, not automatic authority to delete the previous evidence.

### Input precedence and JSON modes

Monolith §3 says JSON is the primary data source and GBK a fallback. Current `parse_bgcs_from_zip` constructs its BGC inventory from region GenBank records, falling back to other GenBank records, while source FASTA/full GenBank contributes source-contig context and assembly metrics. Separate evidence parsing reads TXT clusterblast/KCB files first and adds selected JSON evidence. A project-level master JSON, workbook or prior-session snapshot is not interchangeable with an antiSMASH input archive or its canonical source records. Bind each source to its role and exact path/hash rather than allowing the historical hierarchy to select a different file implicitly.

The run CLI defaults to `--json-evidence bounded`; profile overrides can change this. Its requested mode, effective mode and separate record-level requests must be read together. `off` disables the main JSON walker; it does not promise that no JSON is opened. The CLI status parser requests TIGRFAM through the separate record path, and structured overrides can also request JSON record evidence. If bounded mode lacks ijson, the main walker falls back to off while requested record evidence remains separately scoped. A bounded time-budget fallback also retries the off status path outside the expired budget. “Bounded” is not a universal process-time/RAM cap or a guarantee that every source record/evidence category was parsed.

Current main-walker limits include file-byte and selected matched-leaf limits; despite historical variable names, its selected-leaf cap is not a count of all biological records. `full` is a legacy selective flatten of KCB/cluster-comparison/RiQ/MIBiG-related values, with an 80,000,000-byte uncompressed JSON input cap; it is not a full-source retention mode or RAM limit. Separate record extraction has its own streaming/fallback/size behavior. Read `AntiSMASH_Evidence_Parse.json` fields such as json_mode_requested, json_mode, json_parse_budget, json_skipped, json_errors, json_bounded_truncated, schema_warnings and mapped/unmapped evidence counts before inferring coverage. A mode label or JSON filename alone does not establish complete interpretation.

Region-only archives can support region inventory while leaving original-contig/whole-assembly context unavailable. Do not treat clipped region length as source-contig length or absent record JSON as absence of a diagnostic pathway. Partial archives, skipped input, unknown schemas, extraction errors and unbound evidence are workflow/coverage states; keep them distinct from a source-supported negative. The monolith's per-BGC requested fields include judgment, context and optional evidence, so their listing does not establish that each current deterministic row supplies them. Full locus identity remains strain / full node-or-contig / region / BGC alias; aliases or flattened values alone do not prove source binding.

## Literature input limitations

- **Workflow versus owner scope:** `literature_intake` parses sequential PubMed-export text, records DOI/PMID/PMCID/title/authors/citation and line spans, applies keyword-first routing, and writes TSV/JSON plus a receipt. Its explicit status and holds exclude query-locus admission; it does not execute the full nine-step publication workflow or produce §21's six-sheet workbook. `literature_lookup` reads JSONL and does keyword matching. Do not infer bundle-wide citation-verification capabilities from these two intake/lookup commands.
- **Typed unavailable/readiness hold:** `load_corpus` returns {} for absent path, skips JSONDecodeError lines and silently overwrites repeated PMID keys. `abstract_for` returns an empty string for absent records or missing abstracts. `stats.corpus_present` uses bool(parsed records), rather than actual file existence/readability. Empty or all-malformed existing files therefore share that false status with an absent corpus. Malformed record types/read failures are not all caught. These facts bound this owner; they are not evidence about any real corpus.
- **Refresh and duplicates hold:** maxsize1 lru_cache keys only the supplied path argument. A path unchanged on disk or the default None key can retain a prior record snapshot after file/env changes. Duplicate PMIDs have last-row-wins policy without conflict receipts. A future typed loader should bind source hash/snapshot, distinguish absent/empty/invalid/loaded/partial and report invalid lines plus duplicate/conflicting keys; refresh must be explicit or fingerprint-aware.
- **Hash-label hold:** intake144–148 decodes UTF-8-sig/read_text then hashes the re-encoded normalized string for each record's source_file_sha256. Receipt230 hashes raw binary source through sha256_file. BOM removal/universal newline conversion can make those identifiers differ. The two digest representations are not interchangeable. Rename the normalized digest or bind raw bytes consistently, retain both identities if needed, and record transformation/version semantics.

### Evidence required before reuse

Distinguish absent, empty, invalid, partial and loaded corpus states. Retain duplicate/conflicting PMID records, missing abstracts and the source hash for the selected snapshot. After replacing a corpus or changing its resolved path, verify an explicit refresh before reuse. Keep raw-byte hashes separate from normalized-text hashes and record BOM/newline transformations. Parsed bibliographic metadata remains discovery input until independently verified and admitted to the claim.

Record unresolved corpus, citation and metadata states alongside the selected literature records.

Per-strain construction and aggregate master re-ingest have different overwrite/annotation contracts; preserve external annotations and original source evidence before a separately authorized rebuild.

### Scoping literature versus citation work orders

Monolith §§22–23 describe an authored scoping bibliography and Gaps Analysis, followed by separately verified synthesis when needed. The historical paper-count ranges, word targets and escalation thresholds are workflow guidance, not evidence that a search, source verification, extraction or synthesis happened. Report the actual searched/selected/read/verified denominators, source access limits and unresolved questions. A work order is a request for evidence, not an adopted finding or authorization to perform external searches/jobs.

The helper in `mamey/citations/resolver.py` classifies supplied citation context and emits citation CSVs, a Markdown work order and a receipt. It does not perform the six-step scoping review, generate the historical three-sheet bibliography workbook, independently resolve DOI/PMID metadata or read primary papers. Its `PASS_STRUCTURE` and `PASS_VERIFIED_PRIMARY` labels are code-status aggregates, not independent paper-verification verdicts. The latter can currently arise from method/database/user-supplied labels; preserve those evidence types separately from verified primary findings.

Keep declared citation status, source verification, relevance, claim support and manuscript adoption distinct. A DOI/PMID-shaped string or supplied verified label does not establish a checked paper or support for a particular claim. Retain conflicting statuses and full `strain / full node-or-contig / region / BGC alias` rather than merging only a locus tag/context. Missing input discovery, an empty work order and no unresolved rows are different states; none proves that all required papers or claims were checked.

`schemas/literature_search_workorder_v1.schema.json` describes a separate search-task structure. It is not the citation-resolution receipt schema, and structural validity alone does not prove populated tasks, exact identity, duplicate-free coverage or executed searches. Before a maintainer integrates any repair, require explicit source-backed verification/adoption and preserve unperformed/held work. References: `mamey/citations/resolver.py`, `schemas/literature_search_workorder_v1.schema.json`, and monolith §§22–23.

### Family seeds versus cross-strain GCF tables

Monolith §35's authored family-seed labels and review thresholds are historical project-planning guidance. They do not establish that clustering was executed or that a native workbook contains CrossStrain_Family_Seeds. Current `tools/bigscape_cross_strain.py` summarizes memberships already stored in a BiG-SCAPE SQLite database; it does not run clustering or reconstruct the historical seed workbook. Its default minimum is two filename-derived strain labels, separate from the monolith's three-strain recommendation. Old project-specific prevalence/adoption rulings remain historical evidence, not current portable cohort facts.

Retain the exact run ID, normalized cutoff and qualified family identity owned by `mamey/bigscape_namespace.py`. A bare family number, seed label, class label or reference member is not portable grouping identity. Family membership and comparator presence do not establish product identity, activity, production, physical linkage or scientific acceptance. When individual loci are listed, require `strain / full node-or-contig / region / BGC alias` and a bound input/source mapping.

The current table's `n_strains` counts unique nonreference labels parsed from filenames; `n_members` counts unique nonreference locators. Its `dominant_product` counter includes all joined membership rows, including reference rows, and is a display summary with a different denominator. Unknown filename-derived labels and broad reference-name detection need separate held admission; do not report them as verified strains. Declare requested/stored cutoffs, source database/run scope, selected/omitted members and unresolved identities before comparison.

Optional parking filters apply to `dominant_product` and write a separate parked table/filter receipt. They are explicit display/export scope, not absence calls or biological family judgments. Review actual full membership before interpreting a filter label. A header-only table, missing run, unavailable database or skipped family is not evidence that no family exists. Source-database admission, complete identity binding, retained membership and scientific/editorial adoption remain independently verified.

References: `tools/bigscape_cross_strain.py`, `mamey/bigscape_namespace.py`, monolith §35 and the current workbook-contract guidance.

Before using `--db`, confirm it points to an existing readable database with the expected schema. The current helper opens SQLite in ordinary create/write mode: a missing path can create an empty database and then fail its query. Preserve the source database and bind its hash externally. Use a new output filename; each TSV/sidecar is replaced atomically on its own, but the output set is not one transaction. A failed later write can leave a partial set, and old filter sidecars can remain when a later invocation has no filter. Keep current outputs and prior artifacts distinguishable.
